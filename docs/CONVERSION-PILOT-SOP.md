# 保存成功与转化试点 SOP

## 发布范围

beta.7 提供转化模块，默认关闭。先完成一个站点的真实验收及报表对账，再决定稳定发布和其余站点迁移。测试版本不进入现有稳定自动升级渠道。参考站只读，账号标识不得复制到试点站。

## 站点配置清单

- 本站域名、原生记录 metadata、询盘编号前缀、队列前缀、小满账号及来源/产品映射。
- 两个 Bricks 原生询盘表单：字段语义名、保存动作 → 小满询盘 → 原有后续动作。
- 本站感谢页及 TranslatePress 实际语言路径；`form=quick_quote` 两种表单共用，`form_type=quick/detail` 区分。
- 现有单一 GTM 容器、GA4 衡量 ID、Ads 转化 ID、表单标签、可选的 WhatsApp/邮箱次要标签。
- 已发布的 Real Cookie Banner 服务 Unique Name 及用途：`analytics_storage`、`ad_storage`、`ad_user_data`。Google 同意模式由现有 CMP 管理，插件不授予同意。
- 归因服务声明实际使用的四个 `xi_*` 存储键，兼容期保留原站旧键。准备声明会合并已有键，不删除本站声明。
- Google Ads 落地 URL 实际传入 campaign/adgroup/keyword/device 等参数。仅 click ID 无法推算广告系列名称；Cloudflare 不负责补出它们。
- 按广告类型确认参数可用性。Performance Max 无关键词匹配时 keyword 可为空；其素材组与搜索广告组含义不同，不把不可用字段伪造为广告组。参考 Google 官方 ValueTrack 支持范围：https://support.google.com/google-ads/answer/6305348?hl=en 。
- Cloudflare/源站不得缓存 POST、admin-ajax 或询盘后台；感谢页含临时凭据时不缓存。核对国家识别、广告参数保留、WAF、脚本延迟/合并和重定向。
- 分别记录网站、GA4、Ads 时区。对账按真实转化时间统一换算，不能拿点击日期列对网站提交日期。

## 备份和接管

1. 在源站私有目录备份数据库、插件、Bricks 表单、追踪代码、Cookies 服务、翻译配置。验证 SHA256，并保存原记录数量/编号边界/记录哈希。
2. 导出当前已发布 GTM 容器，确认没有他人的待发布变更。记录旧标签、触发条件、Google 目标和 Ads 主次角色。
3. 安装经过签名和哈希核验的测试包，保持转化模块关闭。确认旧客户记录、队列及表单仍可读取。
4. 配置本站目标和同意服务。GTM ID 仅登记，插件不重复安装容器。感谢页脚本必须在 Google 基础代码前移除临时凭据；检查优化插件和浏览器实际执行顺序。
   - 原生语言路径必须回读实际发布页面，不能假定所有翻译路径都是 thank-you。语言路径已经带前缀时，不再叠加经翻译过滤的 home_url。
   - 每次安装或升级后清理源站缓存与对应站点的 Cloudflare 页面缓存，检查匿名访客英文及主要语言页面实际加载的插件版本。边缘缓存忽略源站响应头时，仅清理 WordPress 缓存不足以更新 HTML。
   - 检查 Cookie 设置按钮可以打开、同意组件资源没有失效、同意后 Google 基础代码可以加载。确认 Google 基础代码的实际发送目标包含本站 GA4 和 Ads；不要仅凭全局 gtag 函数存在判定目标已经初始化，也不要重复安装 GTM。
5. 准备暂停对应旧表单/联系点击事件标签的 GTM 草稿，保留基础 Google 代码及转化链接器。切换时记录发布/启用 UTC 时间及询盘编号边界；将切换窗口单独列入对账。
6. 启用统一转化配置时自动取现有最大询盘 ID 作为历史边界。只有新保存的询盘可领取临时凭据，普通历史感谢页链接不触发事件。
7. GA4 `generate_lead` 为表单关键事件；Ads 原生表单主要，GA4 导入次要。`whatsapp_click`、`email_click` 独立观察，不能当作表单成功。

## 去重和交付证据

保存成功后，响应带唯一编号、`redirectTo`（旧字段存在时同时更新 `redirectUrl`）和 30 分钟随机凭据。凭据只存于当前页面内存，URL 立即清除，不写浏览器持久存储。服务端仅存凭据哈希。

每条询盘每个目标只有一次原子发送资格。多标签页并发、返回、刷新、重复原始链接均不能再领取。同意拒绝不领取；同意撤回不发送。GA4 参数不带姓名、邮箱、电话。增强型数据仅在提交及发送时均同意 `ad_user_data` 时规范化、SHA256 后提供给 Ads，随后清除全局用户数据。

`claimed` 表示一次发送资格已领取；`callback` 只表示 Google 标签回调（含超时回调），**不证明 Google 已入账**。网络中断、离页、拦截器仍可能造成已保存而未入账。禁止把这类情况自动重发成第二条转化；按后台记录和报表逐项解释差额。

## 真实测试授权和矩阵

提交前告知测试数量、明确标记的字段、网站记录、小满记录及原有通知规则可能产生的通知，并获得授权。未授权时只做本地阻断外部 HTTP 的测试。

验收至少覆盖：快速/详情、英文及主要语言、电脑/手机、校验/保存失败、拒绝及接受同意、感谢页刷新/返回/重复打开、CRM 明确失败重试、结果不明时禁止盲目重建。按编号记录预期/实际结果。测试询盘标记 `XI-PILOT-TEST-`，通过限时邮箱白名单标记 `is_test`；单独排除报表中的测试，不能假装它们是实际广告点击。

测试用例名不能代替实际表单 ID 和服务端 form_kind。电脑缩小视口只证明移动布局；真实手机须记录设备及浏览器、实际表单、感谢页编号和两路证据。达到授权数量后关闭测试白名单，移除隔离故障文件；不重复提交已经保存的记录。

## 分阶段及对账

初次表单、已核实的小满 ABC 合格客户、已核实的订单成交分别保存在本地阶段表。后两者目前由管理员核实等级/订单及含时区的实际发生时间后记录；不是自动查询 CRM 等级，也不会自动上传客户数据到 Google。

对账表按询盘编号保留：实际提交 UTC/统一时区日期、表单种类、测试/重复标记、同意状态、保存结果、CRM 状态及现有 ID、GA4 发送资格/回调/报表、Ads 原生及 GA4 导入的实际转化日期列、差额原因。两条 Ads 路径是同一批线索的对账，不相加。

预留 Google 报表处理时间，复核 24–48 小时后结果及尚未处理数据。同意拒绝、自然流量、广告归因窗口和按转化日期/互动日期的差异分别说明。未形成对账证据，不判定验收通过，不推广其他站。

增强型转化实际核验还须取得 Ads 请求中的目标、transaction_id 及规范化哈希证据，并复核处理后的诊断。Google 官方说明诊断通常约 72 小时后可查看：https://support.google.com/google-ads/answer/13258081?hl=en 。调试工具未连接或只有标签回执时，记录待验收，不能宣告增强型转化成功。

## 回滚

先关闭本站新转化配置，再恢复已备份 GTM 版本和旧事件标签，记录恢复时间。恢复前核对是否有接管期间新询盘，避免对其感谢页重新打开造成旧标签计数。

将插件文件恢复到原版本，按备份恢复本次更改的转化配置、Cookies/缓存优化设置。保留新增询盘、CRM 队列、已创建 ID、阶段及去重账本；不要整库覆盖回试点前数据库。历史完整 SQL 是灾难恢复材料，不是日常回滚步骤。复核原生保存、同步状态、前台、后台和原追踪后再宣布回滚完成。
